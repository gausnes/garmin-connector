# garmin-connector

Cloudflare Worker serving a stateless MCP server (Streamable HTTP, JSON responses) over Garmin's official Connect Personal API. Public repo, MIT.

## Layout
- `src/index.ts`: Worker entry. Auth via `/mcp/<MCP_PATH_SECRET>` or `Authorization: Bearer` on `/mcp`. Builds a fresh MCP server per request.
- `src/garmin/`: the Garmin API client, split by concern.
  - `client.ts`: transport. API key → JWT bearer token (cached in isolate memory, refreshed within 1h of `exp`, retried once on 401). Downloaded activity files are also cached in isolate memory, since `get_activity_fit` pages through one activity with several calls.
  - `api.ts`: `GarminApi`, a typed per-endpoint layer over a `GarminClient` (paths from Garmin's reference client). Types are compile-time only, not runtime-validated, so array-returning methods still defensively fall back to `[]`.
  - `model/`: TS shapes for confirmed response fields, one interface per file (barrel `index.ts`), from live captures against a real account — not a published schema. Endpoints with no confirmed shape (e.g. `hrvSummaries`) stay untyped rather than guessed.
  - `index.ts`: barrel re-exporting `client.ts`, `api.ts`, and `model/`.
- `src/tools.ts`: MCP tool definitions only (schemas + `registerTool` calls) — response shaping lives in `responses/`.
- `src/responses/`: response modeling shared across tool handlers, one file per concern (barrel `index.ts`): `page.ts` (date-range paging + `pageArray` for `get_body_battery_series`), `activity.ts` (summarizing `list_activities` items), `body-battery.ts` (the one typed ref + resolver, see below), `mcp-result.ts` (wraps handler results/errors into MCP `content`/`structuredContent`; null-dropping and BigInt-stringifying both happen in the one `JSON.stringify` replacer the `content` text goes through, not a separate sanitizing pass — though for schema'd tools that replacer never even runs, see below).
- `src/fit.ts`: unzips the original activity file and decodes FIT with `@garmin/fitsdk`, returning the decoded messages as-is, paged (`get_activity_fit`).

## Rules
- Never commit secrets. `GARMIN_API_KEY` and `MCP_PATH_SECRET` live only in Cloudflare secrets and `.dev.vars` (gitignored).
- Keep it read-only and single-user.
- Endpoint paths must match Garmin's reference client (github.com/garmin/connect-personal-api-python, `README.md` endpoint table).
- Run `npm run check` (tsc + `node --test` + wrangler dry-run) before committing.
- Tests run on Node's built-in test runner (`node:test`/`node:assert/strict`), not a separate framework — `describe`/`it`/`beforeEach`/`afterEach` from `node:test`, assertions via `assert.strictEqual`/`assert.deepStrictEqual`/`assert.throws`/`assert.rejects`/`assert.match`. All relative imports use literal `.ts` extensions (`allowImportingTsExtensions` in tsconfig) rather than the `.js`-resolves-to-`.ts` convention bundlers allow, since plain Node ESM resolution needs the real extension on disk; TypeScript constructor parameter properties (`constructor(private readonly x: T)`) aren't usable anywhere in `src/` for the same reason — Node's native type-stripping only erases type syntax, it doesn't transform codegen-requiring syntax like that.
- `GarminClient` tests exercise real `fetch()` against `nock`-intercepted endpoints (`test/garmin.test.ts`, fixtures in `test/garmin-mock.ts` shaped after confirmed real API responses) rather than injecting a fake implementation — prefer extending those over hand-rolled stand-ins.
- Date-range tools page results newest-first (`start`/`limit`).
- `get_activity_fit` with `message_types` set decodes via a `mesgListener` that aborts once `offset + limit` messages of every requested type are seen, so cost scales with the page requested, not the whole file (Cloudflare Workers' free-tier 10ms CPU budget makes full-file decodes of long activities risky otherwise). `counts` becomes a lower bound (`counts_exact: false`) when truncated this way. Only possible when `types` is given — without it, the full file must be walked regardless.
- No generic mechanisms for unconfirmed shapes: no raw-GET escape hatch, and no generic ref-and-JSON-path walking or array-crawling truncation. `get_body_battery_series` is strongly typed to the one endpoint with a confirmed long-array field, `get_body_battery`'s `bodyBatteryValuesArray` (`responses/body-battery.ts`). A tool only gets a typed series ref once its long-array field is actually confirmed against live data and modeled in `model/`. Until then (`get_sleep`, `get_sleep_range`, `get_daily_summaries`, `get_hrv`), responses pass through untouched (aside from the null-dropping every response gets) rather than being guessed at.
- Tools whose response shape we construct ourselves (every paged tool, returning `{ total, start, limit, items }`, plus `get_activity_fit`'s `{ counts, offset, limit, messages, counts_exact, decode_errors }`) declare an `outputSchema` and return `structuredContent` with `content: []` — no `JSON.stringify` call at all. Per `CallToolResultSchema`, `content` "is always present, but it may be empty" once a tool has an `outputSchema`; it exists purely for clients that don't read `structuredContent`, which doesn't apply here (single-user, single Claude client). `items`/`messages` stay `z.unknown()` inside the schema — only the wrapper we own is validated; Garmin's own nested shapes stay compile-time-only per the model-typing rule above. `get_sleep`, `get_activity`, and `list_activities` don't get an `outputSchema`: their whole top-level response is Garmin's own shape with no wrapper of ours to validate, so a real schema would mean either validating Garmin's shape (against the rule above) or a no-op `passthrough()` that adds nothing — these keep building a real `content` text block.
- All tools set `annotations: { readOnlyHint: true, idempotentHint: true, openWorldHint: true }`: every tool is a pure read (idempotent regardless of whether paging args are passed explicitly or defaulted — idempotence is about the call having no additional effect on repeat, not about the response being byte-stable while Garmin's own data changes between calls) against a live external system (`openWorldHint`).
- `structuredContent` bypasses the `content`-text `JSON.stringify` call, so it can't contain a `BigInt` (the transport will eventually serialize it with no replacer to catch one). FIT-decoded data is the only place a `BigInt` can appear; `get_activity_fit`'s handler runs its own result through `bigIntSafe()` before returning, rather than threading that concern through the shared `ok()`/`run()` helpers. Every other tool's `structuredContent` just reuses its `data` directly — Garmin's REST JSON responses never contain one.
